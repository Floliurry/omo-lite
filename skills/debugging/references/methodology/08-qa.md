# Runtime Verification

Use the interface that exercises the reported failure. Reuse a faithful test or reproduction already run; a separate manual pass is useful when it checks a boundary that those checks miss.

| Failure surface | Useful verification |
| --- | --- |
| CLI | Run the relevant command and check output, exit status, and expected side effects. Use a PTY only for terminal interaction. |
| HTTP API | Exercise the failing request through the relevant server path and inspect status, response content, and state changes. |
| Browser state or interaction | Use an available browser interface to reproduce the flow. HTTP calls alone cannot prove viewport, DOM, cookie, or interaction behavior. [Playwright](../tools/playwright-cli.md) is one option, not a required provider. |
| Agent or LLM pipeline | Exercise the relevant input and inspect the semantic result, error fields, and expected tool effects. Usage counters alone do not prove success or failure. |
| Background job | Verify the trigger, processing, and resulting state when the defect crosses those boundaries. |
| MCP server | Use an available protocol client when handshake or tool dispatch is part of the defect. A health endpoint cannot establish protocol correctness. |
| Native or bundled binary | Re-run the relevant input and check output, signal or exit status, and side effects. A decompiler or exploit framework is not a prerequisite. |
| Leak or long-running behavior | Compare resource growth over a relevant workload or duration; a short startup check does not prove a leak is fixed. |

When the environment prevents the relevant run, use [partial runtime evidence](partial-runtime-evidence.md) and state the untested boundary. Do not install a different toolchain solely to satisfy this table.

## Silent failures

When the symptom is a silent failure, inspect the result the caller relies on:

- A successful status with an error field or a missing expected payload.
- A task that completes before its async work, or an exception that never reaches the caller.
- A reported write or job completion without the expected state change.
- A cached response that is inconsistent with the operation's contract.

An empty response or zero usage can be valid for some operations. Judge these signals against the requested behavior, not a universal success rule.

Record the scenario, relevant observations, and outcome in the current task's evidence. Capture screenshots or transcripts when they demonstrate the behavior or are part of the deliverable; no separate journal or reviewer is required.
